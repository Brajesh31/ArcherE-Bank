# 🏦 Project overview

## Purpose

ArcherE-Bank is a banking-interface learning prototype built to explore a web frontend connected to a separate HTTP and real-time backend. Its user-facing surface includes account login and registration, dashboard content, card-style visuals, transfer and request interfaces, and activity views.

The repository is not a licensed financial institution, a payment processor, or a production account ledger. Its card-like data is generated by application code and must not be represented as real payment credentials.

## Problem context

Banking applications provide a useful case study because one user action may involve multiple layers: input validation, identity, business rules, persistence, response handling, and UI synchronization. The prototype places these concerns in a compact repository so developers can inspect the relationships.

## Objectives

1. Demonstrate a modern React/Next.js application structure.
2. Show how a browser application can communicate with an independent Express service.
3. Illustrate SQL persistence for account-like and activity records.
4. Explore request state and transfer history.
5. Demonstrate live activity refresh with Socket.IO.
6. Make the security and reliability requirements of financial workflows visible to developers.

## Scope

### Included in the current repository

- Next.js App Router pages and components.
- TypeScript UI code and CSS Modules.
- Separate Express server.
- MySQL connection module.
- User and card-like record creation.
- Login lookup and cookie creation.
- Balance lookup and activity retrieval.
- Transfer and payment-request routes.
- Socket.IO event handling.

### Explicitly outside current scope

- Actual bank integration or regulated account access.
- Real payment-card issuance or processing.
- Compliance certification.
- Production identity verification.
- Production-grade authentication, fraud prevention, or ledger guarantees.
- Verified deployment, uptime, or service-level commitments.

## Intended users

- Students learning frontend/backend integration.
- Developers studying Express routes and SQL queries.
- Contributors interested in secure workflow redesign.
- Reviewers assessing how a financial-style prototype should evolve.

## Success criteria for a learning release

A learning release should install reproducibly, start locally using disposable data, document its true system boundaries, explain failure cases, and not imply that prototype credentials or balances have monetary value.

Security remediation is a prerequisite for any expansion toward real-user use. See [security review](security-review.md).
