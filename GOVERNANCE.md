# 🏛️ Project governance

## Ownership

Maintained by Brajesh Kumar, [@Brajesh31](https://github.com/Brajesh31).

## Decision process

Routine fixes and documentation updates may be proposed through issues and pull requests. Significant architecture changes should explain context, alternatives, security/privacy impact, API/database compatibility, migration and rollback plan, test evidence and acceptance criteria.

Use an Architecture Decision Record for decisions affecting long-term boundaries or data ownership.

## Sensitive features

Authentication, account identity, card-like values, balances, transfers, requests and socket authorization require explicit risk review and tests. The project remains educational until critical security and correctness gates are addressed.

## Releases

Record notable work in the changelog. Do not label releases production-ready unless security, quality and operations requirements are met. Contributors must follow CODE_OF_CONDUCT.md.

## Documentation

Distinguish current implementation from recommendations. Verify diagrams and project trees against source. Never invent deployment URLs, screenshots, test outcomes or feature status.
